# Общая информация

## Установка ПО в Linux

В Linux существует несколько способов установки программного обеспечения. Выбор способа зависит от:

 - дистрибутива,

 - доступности нужной программы в репозиториях,

 - требований к версии ПО.

1. **Пакетные менеджеры**

Пакетные менеджеры — это инструменты, которые позволяют устанавливать, удалять и обновлять программное обеспечение, а также автоматически управлять его зависимостями. Программы распространяются в виде пакетов, содержащих скомпилированные файлы и метаданные, необходимые для установки.

Пакет — это формат, в котором распространяется программа.

Пакетный менеджер — инструмент для установки, обновления и удаления пакетов.

Основные особенности пакетных менеджеров:

 - используют репозитории, связанные с конкретным дистрибутивом;
 - позволяют устанавливать, обновлять и удалять программы;
 - автоматически разрешают многие зависимости между пакетами;
 - версия программы в репозитории может отличаться от самой новой версии, доступной на сайте разработчика.

Наиболее распространённые пакетные менеджеры:

 - APT — используется в Debian, Ubuntu и других Debian-подобных системах;
 - YUM — используется, в частности, в CentOS 7;
 - DNF — современный наследник YUM, используется в Fedora и современных версиях RHEL/CentOS;
 - Zypper — используется в openSUSE и SUSE Linux Enterprise;
 - Pacman — используется в Arch Linux и его производных.

Пакетный менеджер работает с определённым форматом пакетов, принятым в дистрибутиве. Например, APT используется для управления пакетами .deb в Debian/Ubuntu, а YUM — пакетами .rpm в CentOS 7.

В рамках данной работы используются традиционные пакетные менеджеры:

Debian:

```console
sudo apt install apache2 nginx
```

CentOS 7:

```console
sudo yum install httpd nginx
```

2. **Установка через графический интерфейс**

Пакетными менеджерами можно пользоваться не только через командную строку. Некоторые Linux-системы предоставляют графические приложения, через которые можно искать, устанавливать, обновлять и удалять программы.

По принципу работы они часто являются графическим интерфейсом к существующей системе управления пакетами.

Примеры:

GNOME Software;
KDE Discover;
Ubuntu Software.

Такой способ особенно удобен для пользователей, которые предпочитают графический интерфейс командной строке. При этом те же операции обычно можно выполнить из терминала.

3. **Универсальные системы распространения приложений**

"Продвинутая версия" пакетных менеджеров. Предназначены для того, чтобы одно приложение было проще распространять между разными дистрибутивами.
Позволяют устанавливать приложения на разных дистрибутивах Linux независимо от их стандартной системы пакетов.

Особенности:

 - поддержка разных дистрибутивов;
 - зависимости могут поставляться вместе с приложением;
 - приложения могут занимать больше места;
 - некоторые системы обеспечивают изоляцию приложений.

Примеры: Snap, Flatpak, AppImage.

Snap и Flatpak являются системами распространения и управления приложениями, а AppImage — форматом переносимого приложения.

4. **Ручная установка готового пакета**

Некоторые разработчики распространяют уже скомпилированные пакеты. Пользователь скачивает такой пакет и устанавливает его вручную.

Наиболее распространённые форматы:

.deb — Debian и производные;
.rpm — Red Hat, CentOS и другие RPM-based системы.

Например, DEB-пакет можно установить с помощью:

```console
sudo apt install ./package.deb
```

RPM-пакет в CentOS 7 можно установить с помощью:

```console
sudo rpm -i package.rpm
```

Ручная установка готового пакета может быть удобна, когда нужной версии программы нет в стандартных репозиториях. Однако обновления такого ПО могут потребовать дополнительных действий.

Отдельно существуют форматы распространения приложений, такие как AppImage, Snap и Flatpak. Они имеют собственные механизмы установки и обновления.

5. **Установка программы из исходного кода**

Если ничего другого не осталось — можно самостоятельно собрать программу из исходного кода.

Обычно процесс выглядит следующим образом:

Исходный код
     ↓
Настройка сборки
     ↓
Компиляция
     ↓
Установка

Например:

```console
./configure
make
sudo make install
```

Однако конкретные команды зависят от проекта. Вместо ./configure и make могут использоваться другие системы сборки, например CMake, Meson или другие инструменты.

Преимущества (сомнительные):

 - можно установить версию, которой нет в репозиториях дистрибутива;
 - можно самостоятельно выбрать параметры сборки.

Недостатки:

 - необходимо самостоятельно устанавливать зависимости для сборки - ответственность за совместимость и обновление переносится на пользователя;
 - установленные таким способом файлы не всегда учитываются пакетным менеджером - удаление и обновление программы может быть сложнее;
 - может появиться конфликт с версией, которую установил пакетный менеджер;
 - плохо написанный Makefile теоретически может изменить системные файлы или настройки.

## Дистрибутивы Linux. Основные отличия CentOS от Debian

Дистрибутив Linux — это операционная система, построенная на базе ядра Linux. В состав дистрибутива входят ядро, системные утилиты, пакетный менеджер, репозитории и другие компоненты.

### Debian

Debian — один из наиболее распространённых дистрибутивов Linux. На его основе построены, например, Ubuntu и другие системы.

Основные особенности:

 - использует пакеты формата DEB;
 - основной пакетный менеджер — APT;
 - для управления службами используется systemd и systemctl;
 - большое количество программ доступно через официальные репозитории.

Например, установка Apache и Nginx:

```console
sudo apt update
sudo apt install apache2 nginx
```

### CentOS

CentOS — дистрибутив, связанный с экосистемой Red Hat и традиционно ориентированный на серверное использование.

CentOS 7:

 - использует пакеты формата RPM;
 - основным пакетным менеджером является YUM;
 - для управления службами используется systemd и systemctl;
 - конфигурация и расположение некоторых файлов отличаются от Debian.

Установка Apache и Nginx:

```console
sudo yum install httpd nginx
```

При этом CentOS 7 является устаревшей версией: её официальная поддержка завершилась 30 июня 2024 года. Поэтому стандартные репозитории CentOS 7 были переведены в архив, что может создавать проблемы при установке пакетов.

# Подводные камни

### а) Почему в Debian установились два веб-сервера, но заработал только один?

Потому что Apache и Nginx по умолчанию оба пытаются занять порт 80.

Один процесс может первым занять :80, а второй уже не сможет привязаться к этому порту.

Поэтому установка обоих пакетов прошла успешно, но одновременно работать на одном endpoint <IP>:80 они не могут.

Решается так:

Nginx  → :80
Apache → :8080

## б) Почему в CentOS установились два веб-сервера, но ни один не заработал?

В CentOS 7 после установки httpd и nginx они могут быть установлены, но не запущены автоматически. Кроме того, если оба настроены на :80, при попытке запуска второго возникнет тот же конфликт портов.

То есть нужно различать:

пакет установлен ≠ служба запущена

Можно проверить:

systemctl status httpd
systemctl status nginx

И отдельно проверить, кто слушает порты:

ss -lntp

Если на :80 ничего нет — значит ни один сервис сейчас не слушает этот порт.

## в) Как узнать, что им мешает? Как сделать, чтобы они запускались при старте?

Есть несколько полезных проверок.

1. Проверить состояние сервисов:

Debian:

systemctl status apache2
systemctl status nginx

CentOS:

systemctl status httpd
systemctl status nginx

2. Посмотреть, занят ли порт:

ss -lntp

Например:

LISTEN ... 0.0.0.0:80 ... nginx

означает, что 80 уже занят Nginx.

3. Посмотреть ошибку запуска:

journalctl -u nginx

или:

journalctl -u apache2

Для CentOS:

journalctl -u httpd

Если проблема в занятом порте, в логах обычно будет сообщение примерно о невозможности привязаться к адресу/порту.

Как настроить запуск при загрузке системы

Для Debian:

sudo systemctl enable apache2
sudo systemctl enable nginx

Для CentOS:

sudo systemctl enable httpd
sudo systemctl enable nginx

enable означает:

запускать этот сервис автоматически при загрузке ОС.

А start означает:

запустить его прямо сейчас.

Поэтому обычно:

sudo systemctl enable --now nginx

Это одновременно включает автозапуск и запускает сервис сейчас.

Для Apache аналогично:

Debian:

sudo systemctl enable --now apache2

CentOS:

sudo systemctl enable --now httpd

Но перед этим нужно правильно развести порты:

Nginx  → 80
Apache → 8080
## г) Почему в Debian дефолтная страница веб-сервера открывается, а в CentOS нет?

Потому что в Debian после установки Apache обычно уже есть готовая базовая конфигурация виртуального хоста и стандартная страница Apache, а сервис может быть автоматически запущен установочным процессом.

В результате:

Браузер
   ↓
Debian:80
   ↓
Apache
   ↓
стандартная страница Debian Apache

В CentOS 7 ситуация может отличаться: установка httpd не означает, что служба уже запущена и доступна извне. Нужно проверить:

systemctl status httpd

Если остановлен:

sudo systemctl start httpd

И проверить:

curl http://localhost

Если локально работает, но с другой машины не открывается, тогда уже нужно проверять firewall:

sudo firewall-cmd --list-all

И открыть HTTP:

sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --reload

Для CentOS также может иметь значение SELinux, особенно когда мы позже перенесём Apache с 80 на 8080.

Как это можно коротко сформулировать для отчёта

Главная логика такая:

Установили Apache + Nginx
          ↓
Оба по умолчанию хотят порт 80
          ↓
Один порт нельзя одновременно занять
          ↓
Возникает конфликт
          ↓
Настраиваем:
Nginx  → 80
Apache → 8080
          ↓
Проверяем systemctl + ss + journalctl
          ↓
Включаем автозапуск через systemctl enable

И важный момент: «установлен», «запущен», «слушает порт» и «доступен по сети» — это четыре разных состояния.
